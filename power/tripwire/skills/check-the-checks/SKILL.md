# check-the-checks — 변형으로 검사를 검사하고, 봉인은 사람에게 넘기기

## 왜 하는가

- 정상 코드에서 통과하는 검사라도 구현을 따라가면(구현 상수 import, 경계 바깥만 생성) 위반을 못 잡는다. 이 약점은 정상 코드에서는 드러나지 않고, 기준을 어긴 코드에서만 드러난다.
- 채택된 검사는 `.kiro/guard/sealed.json`(경로·내용 SHA-256·연결 요구사항)에 오른다. 문지기는 봉인된 파일에 대한 쓰기와 그 경로가 들어간 셸 명령을 막고(그 요구사항에 사람이 '스펙을 고친다'를 승인한 동안만 예외), `guard check`는 봉인된 파일의 내용이 바뀌면 그 요구사항을 빨강(`seal-broken`)으로 판정한다. 초록일 때 검사의 기준값을 먼저 8에서 6으로 바꾸고 코드를 바꿔 끝까지 초록으로 지나가는 길이 이것으로 닫힌다.
- 봉인은 검사에 신뢰를 주는 일이라 사람만 실행한다. 에이전트가 고친 검사를 스스로 다시 봉인하는 길을 닫기 위해서다 — 집행 모드의 문지기는 에이전트의 `adopt` 실행을 종료 코드 2로 막는다.

`<guard>`: `.kiro/hooks/tripwire.json`의 command에서 하위 명령 앞부분(예: `node ../guard/dist/cli.js`). 파일이 없으면 setup 스킬 1단계와 같은 방법으로 찾는다.

## 전제

- 대상 검사가 현재 코드에서 통과한다(property-tests 5단계).
- 전체 판정이 빨강이 아니다. 빨강이면 resolve-violation이 먼저다.

## 1. 변형 만들기

변형은 **원본 소스 파일에 쓰지 않는다**. 원본을 변형으로 바꾸면 쓰기 후 검사가 빨강을 기록하고, 집행 모드의 문지기가 원본으로 되돌리는 쓰기까지 막는다. 변형은 JSON으로만 적고, 실행은 사람이 돌리는 `guard adopt`에 맡긴다.

- 위치: `mutants/<spec>/<Rn.m>-m<k>.json` (k = 1, 2, …). 사람이 미리 둔 변형은 `mutants/<spec>/<Rn.m>-h<k>.json`이다 — 고치거나 지우지 않고 2단계 명령 줄에 함께 넣는다.
- 형식:

```json
{
  "requirement": "signup:R2.3",
  "file": "src/signup/validate.ts",
  "find": "export const MIN_PASSWORD_LENGTH = 8;",
  "replace": "export const MIN_PASSWORD_LENGTH = 7;",
  "why": "7자 비밀번호 abcdef1을 받아들여 R2.3을 어긴다"
}
```

규칙:

1. **그 기준만 어긴다**: 기준이 "거절해야 한다"면, 거절해야 할 입력 일부를 받아들이게 만든다. 다른 기준의 동작은 그대로 둔다. 더 엄격하게 만드는 변경(더 많이 거절)은 이 기준의 위반이 아니다.
2. **그럴듯한 실수부터**: 경계값 이동 → 비교 연산자 한 칸(`<` ↔ `<=`) → 복합 조건의 한 부분 누락 → (마지막 수단) 검사 줄 삭제. 줄 삭제 같은 뻔한 변형은 약한 검사도 잡으므로, 그것만으로는 검사를 검사하지 못한다.
3. **숫자 경계가 있으면 변형 2개**: 한 칸 이동(예: 8 → 7, 14 → 13)과 그럴듯한 이동(예: 8 → 6). 둘 다 잡아야 채택된다.
4. `find`는 원본 파일에 **정확히 한 번** 나오는 문자열이고, 바꾼 결과도 컴파일되는 코드다. 한 군데만 바꾼다.
5. `why`에는 이 변형이 받아들이는 위반 입력 하나를 적는다. 그 입력이 기준의 WHEN 조건을 정말 만족하는지 스펙 문장으로 다시 확인한다.
6. 스펙 문장이 바뀌었으면 변형도 새 문장의 경계로 다시 만든다. 옛 변형은 더 이상 위반이 아닐 수 있다.

## 2. 봉인 명령 줄을 사람에게 넘긴다

1. 형식은 guard-check design의 adopt 절을 따른다: `<guard> adopt <spec>:<Rn.m> --test <검사 파일> --mutant <변형 JSON> [--mutant <변형 JSON> …]`. 경로는 작업 공간 루트 기준이고, 그 요구사항의 변형 파일은 사람이 둔 것(`-h<k>`)까지 모두 넣는다. 예: `node ../guard/dist/cli.js adopt signup:R2.3 --test tests/signup/R2.3.prop.test.ts --mutant mutants/signup/R2.3-m1.json --mutant mutants/signup/R2.3-m2.json`
2. 기준마다 명령 줄을 하나씩 보여 주고, 사람이 작업 공간 루트의 자기 터미널에서 실행하게 한다. 이번 응답은 여기서 끝낸다.
3. 에이전트는 `adopt`를 실행하지 않는다. 사용법을 보려고 인자 없이 실행하는 것도 하지 않는다 — 집행 모드에서는 문지기가 종료 코드 2로 막고, hook이 없거나 관찰 모드여도 규칙은 같다.
4. 명령 줄에 `.kiro/guard` 경로를 넣지 않는다. `sealed.json`은 직접 쓰지 않는다.
5. 사람이 실행하면 guard가 하는 일(에이전트가 대신 하지 않는다): 원본 코드에서 검사 파일이 통과하고 그 파일의 태그가 모두 그 요구사항인지 확인 → 변형마다 대상 파일을 잠깐 바꿔 그 검사 파일만 돌리고 원래 바이트로 되돌린 뒤 실패했는지 확인 → 모두 잡으면 `sealed.json`에 기록하고 `sealed <path> for <ID> (<n> mutants caught)`를 출력한다. 하나라도 못 잡으면 `mutant survived: <ID> (<변형 파일>)`를 출력하고 봉인하지 않는다.
6. 사람이 실행했다고 하면 그 출력을 받거나 `.kiro/guard/sealed.json`을 파일 읽기 도구로 읽어 3절대로 처리한다.

## 3. 결과에 따라

| guard adopt 결과(사람이 전한 출력) | 할 일 |
|---|---|
| 채택(`sealed …`) | 보고 표에 적는다 |
| 변형에서 검사가 통과(`mutant survived`) | 검사가 약하다. property-tests 규칙(경계 바로 안쪽 생성, 스펙 숫자, 구현 import 금지, 나머지 입력 유효)으로 그 검사를 다시 만들고 2단계를 다시 한다. 두 번 다시 만들어도 못 잡으면 멈추고 검사·변형·결과를 사람에게 보여 준다 |
| 원본에서 검사가 실패 | 채택할 수 없다. property-tests 5단계의 판단(코드 위반인가, 생성기 오류인가)으로 돌아간다 |
| 검사 파일에 태그 테스트가 없거나 다른 기준의 태그가 섞임 | 기준 하나 = 파일 하나로 나눠 다시 만든다(property-tests 2절) |
| 변형을 적용하지 못함(`find`가 없거나 여러 번 나옴) | 변형 JSON만 고친다 |

못 잡은 변형을 더 쉬운 변형으로 바꿔 채택시키지 않는다.

## 4. 봉인 뒤

- 봉인된 검사 파일은 고치지 않는다. 고쳐야 할 이유(스펙 문장 변경 — 사람이 문장을 고쳐 노랑 `stale`이 된 경우 포함)가 생기면 resolve-violation의 '스펙을 고친다' 흐름으로, 사람이 그 요구사항에 승인을 기록한 동안만 다시 만들고, 다시 봉인할 명령 줄을 사람에게 넘긴다.
- 봉인과 다시 봉인은 언제나 사람이 실행한다.
- 변형 JSON은 지우지 않는다. 무엇으로 검사를 검사했는지의 기록이다.
